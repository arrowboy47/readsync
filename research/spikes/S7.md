# S7: Audiobookshelf app behaviour (2026-11-09 and 2026-11-10)

Script `spikes/s7_abs_cadence.py` (socket.io listener plus REST helpers), raw events in `~/readsync-work/s7_events.jsonl` on Jadu. Book: *This Is How You Lose the Time War* (28 tracks, 15,359 s).

**The phone client is AudioBooth (iOS, "iPhone 15 / v1.13"), not the official Audiobookshelf app.** Everything below describes AudioBooth. The official app was not tested; re-check cheaply if the owner ever switches.

Server: ABS 2.37.1. Socket: connect with websocket transport, emit `auth` with the API key, get `init`. Events seen: `user_item_progress_updated` (carries `sessionId`, `deviceDescription`, `data.currentTime`, `lastUpdate`, `startedAt`), `user_updated`, `user_online`, `user_offline`.

## Step 1: how often does the app report? (C7)
During 5 minutes of playback the app sent one progress update per **~30 s of audio** (30.5 to 31.5 s each). On the clock that was 17 to 34 s between events, median **25.4 s** (the owner listened at about 1.2x). So the lag floor for immersion (C7) is roughly 30 s of audio, about 25 s real time. The last update of a play run was shorter (28.1 s), which fits a final flush on pause.

## Step 2: pause latency (C8)
The pause flushed immediately (the shorter final update at 19:38:00, within seconds of the pause; the owner did not time the tap, so exact latency is not measured). The server knows the pause position within the ~30 s reporting grain at worst.

## Step 3: server-side change while paused (B6)
I set progress forward 2 minutes (6:06 to 8:06) with `PATCH /api/me/progress/{item}` while the app was paused. **The app adopted the new position by itself about 40 s later, without any tap**, and playback then started from my value (server saw 488.5 s two seconds after play). The paused app did not overwrite my write. The server announced my write as `user_updated` (not `user_item_progress_updated`), so the hub must watch both event types and filter out its own writes (R8). Not repeated with the downloaded copy (the book was downloaded afterwards for step 5).

## Step 4: server-side change while playing (B20)
I set progress to 20:00 (1200 s) while the app was playing at ~8:30. **The app ignored it** (no jump), and its next routine save, **19 s later, overwrote my write** with its own position (529 s). Same behaviour as the Kavita web reader: an in-use surface ignores outside writes and wins at its next save. Rule R3 stands: never write into a surface that is playing; a write can only take effect when the app is idle or paused.

## Step 5: offline listening and an offline bookmark (A9, A10)
Airplane mode 20:00 to 20:03 with the book downloaded; played about 3 minutes.
- **Offline listening reaches the server as one lump** after reconnect: a single session update (a client-generated, upper-case session id) with `timeListening` 159.7 s and `currentTime` 997 s. No intermediate positions, and **the time the listening really happened is not recorded**: the server's `lastUpdate` is the arrival time (20:03:25), not 20:00 to 20:03. Activity time (R1) for offline audio is therefore unknown; the hub should treat it as "listened between the previous event and arrival".
- **Offline bookmarks are allowed** in the app and show a "not synced" indicator. The first reconnect did **not** sync them; the owner went offline and online once more and then they synced. Two offline bookmarks arrived together, both stamped with the sync time (`createdAt` 20:08:15), not the time they were made. A bookmark can sit unsynced across a reconnect, so the hub must not assume "online means synced".
- **An online bookmark** reached the server within the same second (`user_updated` at 20:06:35).
- A bookmark change arrives as the generic `user_updated`; the hub re-reads `GET /api/me` (bookmarks list) when it sees one.

## Step 6: long bookmark title (D11)
The app stored a 170-character title unchanged. Server-side test: `POST /api/me/item/{id}/bookmark` accepted and kept titles of 300, 1,000 and 5,000 characters in full (200 OK each, deleted afterwards). **No truncation or limit up to 5,000.** The 60-character title rule in the plan is our own choice for readability, not a server limit.

## Consequences for the build
1. Poll plus socket: subscribe to `user_item_progress_updated` and `user_updated`, and on `user_updated` re-read bookmarks; treat events from our own writes as echoes (R8).
2. Expect the lag floor of ~30 s audio for ABS positions; make the follow-along and the 10 s idle gates in R3 count real playback time, not event arrival.
3. Offline listening is a single batch with the arrival time as its timestamp; bookmarks made offline carry the sync time. Use "arrived at" plus a note that activity time is unknown (R1 fallback).
4. Write ABS positions only when the app has been idle (no progress event for 2 minutes, R3); expect a paused app to adopt the new value on its own within about a minute.
5. The ABS API key used so far belongs to the root (admin) account. Each reader needs a non-admin user and key (K6).
