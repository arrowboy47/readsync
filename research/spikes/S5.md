# S5 — BookBridge spoke contract (read-only code study, 2026-10-21)

Source: `refs/bookbridge` v7.10.0 (65f1cc2). Nothing run; nothing on the live stack touched.

## How annotations flow today
- Canonical store: table `KoreaderAnnotation`, one row per (user, doc md5, `ann_key`). `ann_key = md5("<datetime>|<normalized pos0>")`
  (`db/database_service.py:4323`). Format is KOReader's: `pos0`/`pos1` xpointers + highlighted text + note/color/drawer, `version`,
  `deleted`, `deleted_at`, `source_device`.
- Per-device ack state (`_set_device_state`: `acked_version`, `ack_deleted`) decides what each device or spoke is sent next.
- **Device exchange** `exchange_koreader_annotations` (`:4446`): device sends `{hash, keys[{k,dt}], keysComplete, changes[]}`.
  Hub (1) upserts changes (newer `datetime_updated` wins; a tombstoned row is resurrected only if that device had acked the delete),
  (2) **tombstones every row missing from a `keysComplete` key list that the device previously knew**, (3) returns a per-device delta
  `{toApply:{add,edit,delete}}`. Device then acks.
- **Spokes** (BookOrbit, Grimmory/BookLore, Readest, Hardcover, BookFusion) are in-process services run on a timer
  (`annotation_sync_service.py: run_cycle`). BookOrbit's is the template: each cycle, per user and book:
  `get_annotation_spoke_state(user, md5, SPOKE_KEY)` -> `{keys, changes (rows with version > spoke ack), pending_delete_acks}`;
  POST to the remote; `apply_spoke_annotations(adds, edits, deletes)` merges remote delta into the canonical store (bumps `version`
  so devices pick it up on their next exchange); `mark_spoke_annotations_uploaded(...)`; ack back. Max 50 changes per book per
  call, 5 pull rounds, unmatched hashes rechecked every 6 h.
- Spoke ID columns are per-spoke on the row (`bookorbit_server_id`, `bookorbit_version`, `bookorbit_synced_at`, parameterised via
  `server_id_field` etc.). A new spoke needs new columns (schema migration) or a generic side table.
- Lossy spokes (Grimmory CFI) use `trust_positions=False`: pull never rewrites `pos0`/`ann_key` of a matched row (else the device's
  next key list looks like a delete), content-matches unmatched rows, never revives tombstoned rows from a stale echo.
  **Kavita is a lossy spoke** (XPath without char offset): use that mode.

## Contract a Kavita spoke must implement
1. `list(user, book)` -> Kavita annotations for chapter (`GET /api/Annotation/all-for-series`, filter by chapter).
2. `to_canonical(kavita_ann)` -> `{datetime, pos0, pos1, text, note, color, drawer}`; pos0/pos1 come from quote+prefix/suffix+spine
   resolved against the EPUB (BookBridge `ebook_utils`), not from Kavita's XPath (S8 proves the device side).
3. `from_canonical(row)` -> `POST /api/Annotation/create` (needs chapterId, libraryId, ownerUserId, seriesId, volumeId, xPath,
   selectedText, pageNumber); edits and deletes by Kavita annotation id.
4. Store Kavita id + version per row (new columns), use `get_annotation_spoke_state` / `apply_spoke_annotations(trust_positions=False)`.
5. Deletions go by key omission on our side; to Kavita by explicit `DELETE`. Never delete on missing-from-list without R10 guard.
6. Echo suppression: record `source_device="@kavita"`; ignore Kavita `AnnotationUpdate` events for ids we just wrote (R8).

## ABS-bookmark spoke contract
Same shape, but ABS bookmarks are `{libraryItemId, time, title}` only: map time -> text via alignment map, text -> canonical row;
only canonical rows with a note become ABS bookmarks (Q3). No pos0 trust either (`trust_positions=False`). Uses ABS `user_updated`
diff or `GET /api/me/bookmarks` (2.36+).

## Spoke-originated items reach devices?
Yes, by design: `apply_spoke_annotations` creates/edits a canonical row and bumps `version`; `_compute_annotation_delta` hands it to
every device whose `acked_version` is lower on its next exchange. Items are delivered only on the device's next exchange (open,
resume, close), not pushed live.

## Answers to the open questions
- **B6, does anything skip the 300 s KOSync PUT debounce on close/suspend?** No. `_record_kosync_event` sets `last_event`;
  `_kosync_debounce_loop` fires the cross-service sync only after `KOSYNC_PUT_DEBOUNCE_SECONDS` (default 300) of **no PUTs**. No
  "closing" signal, no bypass. Fast hand-off after close can lag up to 5 min+10 s loop. Needs a patch: lower default and/or flush
  on device-sync exchange (the plugin already calls exchange on close/suspend: use it as the flush trigger).
- **B7, does it listen for ABS `user_session_closed`?** No. `abs_socket_listener.py` registers only `init`, `auth_failed`,
  `connect_error`, `user_item_progress_updated` (30 s debounce). Session-close is a new subscription.
- **Mass-delete risk (E8) confirmed in code:** step 2 above tombstones any row absent from a `keysComplete` list that the device
  "knew" (`source_device == device` or `acked_version > 0`). There is no count/percentage guard. S9 will reproduce.
- **R3/R1 gaps:** rows carry `datetime`/`datetime_updated` (device clock) but no `activity_at`/`received_at` split; no outbox;
  no compare-and-set on Kavita writes.

## Fork vs sidecar
A sidecar could talk to the hub as an ordinary "device" over `/koreader/device-sync/annotations/exchange` with no code coupling.
But R10 (mass-delete guard), R1 (activity vs arrival time), new row columns (Kavita id/version, `archived_text`, `link_positions`)
and the KOSync flush patch all live **inside** the hub's exchange/DB code and cannot be done from outside.
Spokes are additive files, so a fork stays rebase-friendly if we keep patches to hub internals small and numbered.

Decision: fork
(Fork of cporcellijr/bookbridge pinned to v7.10.0. New code in new files: `kavita_annotation_spoke.py`, `abs_bookmark_spoke.py`,
`fable_client.py`, `o_rollup.py`; hub patches limited to: R10 guard in exchange, debounce flush on exchange/close, `user_session_closed`
listener, new columns migration. Each patch tagged `readsync:` in source for rebase.)
