# S11 — Two-reader isolation (2026-11-02)

BookBridge 7.10.0, throwaway container on thebigbox (`--network none`, scratch SQLite). Script `spikes/s11_two_readers.py`, result `S11.json`. Two users created (owner = admin, partner = user), same book hash.

| Case | Result |
|---|---|
| K1 same hash, two readers | Each reader's position is stored separately (A 25 %, B 80 %); neither overwrites the other. Per-user table `kosync_user_progress`, keyed by (hash, user). |
| K3 annotation isolation | Reader B, using the **same device key** as A, is offered 0 of A's 5 highlights. Exchange key includes the reader. |
| K4 wipe is per reader | B's wiped sidecar tombstones only B's 3 highlights; A's 5 stay live. A's own wipe does not touch B. |

## Findings to carry into the build
1. **The shared `kosync_documents` row has the hash as its only primary key** and is overwritten by whichever reader wrote last (it is a cache plus the hash→book link). The authoritative per-reader value is `kosync_user_progress`, and BookBridge's PUT path compares against that, so progress is safe. But anything we write that reads `kosync_documents` directly would mix readers. **Rule for our code: read positions only through the per-user functions.**
2. **`_resolve_uid()` falls back to the first admin when no user is given** (it logs a warning). A spoke that forgets `user_id` would silently write the partner's data into the owner's account. Every call in our spokes passes `reader_id` explicitly, and a test fails if the warning appears in the log (K6).
3. Alignment maps and the hash→book link are shared by design; that matches K5 (shared, read-only).
