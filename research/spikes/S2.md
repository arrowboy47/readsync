# S2 — Kavita SignalR events and reader behaviour

Script `spikes/s2_kavita_signalr.py` (needs `signalrcore`; venv `~/readsync-work/venv`). Raw events: `S2.json`.

## Findings (API half)
- Hub: `wss://<kavita>/hubs/messages`, JWT as `access_token` (from `POST /api/Plugin/authenticate?apiKey=…&pluginName=…` → `token`). Connects fine; on connect it sends `OnlineUsers` `[["thehusk"]]`.
- `UserProgressUpdate` payload: `{"body":{"userId":1,"seriesId":90,"volumeId":90,"chapterId":102,"pagesRead":5},"name":"UserProgressUpdate","title":"Updating User Progress","eventType":"updated"}`.
  **It carries `pagesRead` only: no `bookScrollId`, no percentage.** The spoke must re-read `GET /api/Reader/get-progress?chapterId=` after each event.
- **Echo (R8): our own REST writes DO fire the event**, 0.04–0.2 s after `POST /api/Reader/progress`. The event has no origin field, so the hub must suppress echoes itself (remember the last value written per chapter for a few seconds).
- **`AnnotationUpdate` did not fire** for an annotation created and deleted through `POST /api/Annotation/create` / `DELETE /api/Annotation` (2 runs, 4–8 s wait each). Either it only fires for UI-originated changes or to other users. Do not depend on it: poll `GET /api/Annotation/all-for-series` (cheap) for the annotation spoke. Re-check once with the owner creating a highlight in the browser (step 3 below).
- Annotation create needs these `AnnotationDto` fields or it returns 400 "missing required properties": `ownerUserId` (1) and `ownerUsername` ("thehusk"), in addition to `xPath`, `endingXPath`, `selectedText`, `pageNumber`, ids, `highlightCount`, `selectedSlotIndex`, `containsSpoiler`, `comment`. With those, create returned 200 and delete 200 (ids 4, 5; both removed, series has 0 annotations again).
- Side effect: restoring "no progress" is not possible through the API. Time War had no progress record (`pageNum 0, lastModified 0001-01-01`); after the test it has an explicit `pageNum 0` record. Harmless, but the spoke must not treat "a progress row exists" as "was opened".


## Reader modes and what "page" means (owner observation + data, 2026-11-10)
- **A Kavita "page" is not a chapter.** Several pages make up one chapter (page 23 of 56 reports `chapterTitle` "Chapter 10"). In scroll mode a page is a slice of a chapter, not the whole chapter.
- **The page count is the same in scroll, 1-column and 2-column mode.** The layout changes only how the page is shown: scroll mode lets you scroll inside the page, the column modes fit all of the page's text on screen with no scrolling. So the `pageNum` is a stable server-side unit, independent of layout (good: it will not shift when the owner changes mode or device).
- **`bookScrollId` is saved in all three modes** (paragraph path inside the page such as `//body/p[34]`, sometimes a span such as `//body/p[8]/span[1]`). Saves come every 1 to 3 seconds while reading, not only on a page change.
- **Saves can land out of order.** In one run an older save (page 6, 02:52:31) arrived after a newer one (page 7, 02:52:37), and the paragraph anchor bounces (`p[1]`, `p[29]`, `p[1]`) while scrolling. The spoke must debounce, then read progress after about 10 seconds of quiet, and must not trust the order of events.
- The hub should still store its own position as chapter plus position-in-text, not as Kavita page, because Kavita pages differ between builds of the same EPUB (E16).

## Browser half, results (owner at the Kavita web reader, 2026-11-10)

**B19: server-side progress change under an open reader.** I set progress to page 40 (`p[3]`) from the server while the reader sat on page 7. The reader **did nothing visible**: no jump, no prompt. It also did not write back immediately (the server held page 40 for the 20 s I watched). Its **next routine save, about 60 s later, overwrote my write** with its own position (page 7, then page 8 after the owner turned a page). The page turn worked normally. So: an open reader ignores server-side progress and silently wins. Writing into a surface in use is lost (rule R3 stands; the hub must wait until the reader has been idle, and must not rely on a write "taking").

**B9: which modes save `bookScrollId`.** All three (scroll, 1-column, 2-column), see the reader-modes section above.

**`AnnotationUpdate` never fires.** Neither for API-made highlights (earlier run) nor for highlights created and deleted by hand in the reader (this run, listener `spikes/s2_listen.py`). The watcher (`spikes/s2_watch.py`) saw both changes in the annotation list, so the data changed; the hub just does not announce it. **Poll for annotations**: `GET /api/Annotation/all-for-series`, or one call to `/api/Annotation/all` for the whole account. Reader progress saves do arrive as `UserProgressUpdate` (carrying `pagesRead` only).
