# S10: Follow-along on the Kindle (2026-11-10)

Result: PARTIAL. Page turns, battery, ghosting and suspend behaviour are measured. The network half is not: the Kindle was away from the home network, so no request could reach the hub host. Repeat the network half on the home Wi-Fi (about 10 minutes) before Phase 3.

Device: Kindle Paperwhite 3, KOReader v2026.07.2. Plugin: `spikes/s8/readsync_spike.koplugin/` (menu items "S10: start/stop follow-along"). Raw log: `S10.log`. The owner stopped the run early.

## Measured
| Item | Result |
|---|---|
| Run length | 1,608 s (26.8 min), stopped by the owner |
| Page turns | 50 (one every 30 s asked for; 11 or 12 per 375 s, so about 31 to 34 s each) |
| Battery | 98 % to 96 % (owner's start and end figures match the log). That is about 4 to 5 % per hour, but the battery reading moves in 1 % steps, so the real figure is between about 2 and 7 % per hour |
| Wi-Fi radio | `isWifiOn` stayed true for the whole run (0 drops logged); the owner saw no drops |
| Ghosting and flashing | None seen by the owner |
| Suspend | The Kindle **went to sleep on its own** during the run. The owner turned it back on and the turns continued. The log cannot say when it slept (the turn count stayed regular up to the end), so suspend timing is unknown |

## Not measured
- **Network reachability.** All 64 requests failed (64/64) because the Kindle was not on the home network. This says nothing about the Kindle's ability to talk to the hub.
- **Whether Wi-Fi survives a suspend** and how long it takes to come back (C9).
- **A full 30 minutes**, and a drain figure better than 1 % resolution (a longer run would help).

## Findings
1. **C10 is confirmed in practice:** software page turns do not keep the Kindle awake. The plugin must hold the device awake while following, or follow-along simply pauses when the Kindle sleeps and resumes when woken (a valid design: R3 says never write into a live surface anyway).
2. **Visual cost is acceptable to the owner** at one turn per 30 s: no ghosting, no flashing.
3. **Battery cost is small** at this cadence, but the figure is coarse.
4. `setAutoStandby(false)` is not enough on its own to stop the sleep seen here; the plugin did not use a wakelock (`device:powerd`/`UIManager:preventStandby` and `PowerD` suspend inhibition) so this is untested.

## Open items before Phase 3
- Repeat on the home Wi-Fi: run the same plugin about 10 minutes, with `preventStandby` called, and confirm requests succeed and Wi-Fi comes back after a sleep.
- Decide the follow-along rule on sleep: stop, or keep the device awake with a battery warning.
